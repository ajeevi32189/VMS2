Executive Summary:   
The application security testing of the  Gyanakshi  web  application  of Ajeevi Technologies Pvt . Ltd. 
was undertaken by STQC  (Service Request Form No: 2605902 ). The scope of testing covered  only the 
web application & did not include any attempts to exploit network or host system level 
vulnerabilities. As the scope was limited to application security only, the configuration settings of 
host systems & network devices and operational aspects in cluding security processes/ controls at 
hosting site were not verified.  
  
The key aim of application security testing was to verify that it complies with the security 
requirements of OWASP Top 10, 2025 . The website application security testing was performed to 
assess the adequacy & effectiveness of various security controls such as input validation, 
authentication, authorization, session management, data protection during transmission and in 
storage, error handling, audit logs etc. and identify the vulnerabilities (if any).  
 
The application security testing was performed only on the test setup which was provided to STQC 
on a staging server and the application was accessed directly by using  https://gyanakshi.com/login  
test URL with  admin  role (User id : admin@demo.com) . Assessment of completeness and correctness 
of the functions implemented in the application was not carried out as it does not come under the 
scope of application security testing.  
 
The Website Application Security Testing was carried out  using black box approach based on test 
scenarios & test cases derived from the requirements of the application without any knowledge of 
the internals. Security testing was conducted without launching any attack; however, tests were 
conducted to determine whether the Website is susceptible to security vulnerabilities. The security 
testing involved an active analysis of Website to identify any weaknesses, technical flaws and 
vulnerabilities. The Website was tested as per the security requirements of OWASP Top 10, 202 5. 
 
During the proposal stage, the URL provided was http://14.195.152.244:9013/ . However, during 
the testing phase, the URL was changed to https://gyanakshi. com/login . Therefore, all security 
testing was conducted on the revised URL, i.e., https://gyanakshi.com/login . 
 
The Security vulnerabilities / findings  (observed through automated and manual testing) are given 
in section 4.0. For evidence of the vulne rabilities, please refer the attac hed snapshots in Annexure 
‘B’ and the Tool reports shared along with this report.

15.  Weak TLS Configuration: Obsolete CBC Cipher Suites Offered  
During the security assessment, it was observed that the application offers obsolete CBC 
(Cipher Block Chaining) cipher suites, as identified in the testssl report. The use of weak or 
outdated TLS  cipher suites may expose the application to cryptographic attacks such as 
padding oracle –based attacks, potentially compromising the confidentiality and integrity of 
encrypted communications. To mitigate this issue, it is strongly recommended to disable 
obsolete and weak CBC -based cipher suites; configure the server to support only strong, 
modern cipher suites (such as AES -GCM or ChaCha20 -Poly1305); enforce TLS 1.2 and TLS 1.3; 
and follow industry best practices for secure TLS configuration.  
Refer  Annexure  ‘A’ - Snapshots of vulnerabilities observed (Sr. No. 6).  
16.  BREACH Offered  
During the security assessment, it was observed that the application offers BREACH (Browser 
Reconnaissance and Exfiltration via Adaptive Compression of Hypertext) vulnerability, as  
identified in the testssl report. BREACH is a side -channel attack that can potentially allow an 
attacker to infer sensitive information from encrypted HTTPS responses by analyzing 
differences in the size of compressed responses. To mitigate this issue, it  is strongly 
recommended to implement appropriate mitigations, such as: disable HTTP compression for 
responses containing sensitive information, avoid reflecting attacker -controlled input 
together with sensitive secrets in the same response, separate sensi tive tokens from pages 
that contain user -controlled input, implement random padding in sensitive responses where 
appropriate, review the application's use of gzip/Brotli compression, and use appropriate 
CSRF protections and secure session management.  
Refer  Annexure ‘A’ - Snapshots of vulnerabilities observed (Sr. No. 7).  
17.  BEAST Offered  
During the security assessment, it was observed that the application offers BEAST (Browser 
Exploit Against SSL/TLS) vulnerability, as identified in the testssl  report. BEAST is a 
cryptographic attack that primarily affects SSL/TLS implementations using TLS 1.0 with CBC 
(Cipher Block Chaining) mode cipher suites . Under certain conditions, an attacker positioned 
as a Man -in-the-Middle (MITM) may be able to exploit  weaknesses in the CBC 
implementation and potentially recover sensitive information from encrypted 
communications. To mitigate this issue, it is strongly recommended to implement 
appropriate mitigations, such as: disable TLS 1.0  and other obsolete SSL/TLS protocols, 
Support only modern protocols, preferably TLS 1.2 and TLS 1.3 , Disable unnecessary CBC-
mode cipher suites , particularly for legacy TLS configurations, Prefer modern authenticated 
encryption cipher suites such as: AES-GCM  and ChaCha20 -Poly1305 , Configure the server to 
use strong key exchange mechanisms such as ECDHE , Regularly review the SSL/TLS 
configuration according to current industry security standards and best practices and Test 
the server configuration after remediation using an appropriate  SSL/TLS security assessment 
tool.  
Refer  Annexure ‘A’ - Snapshots of vulnerabilities observed (Sr. No. 8).

29.  Broken Access Control: Insecure Direct Object Reference (IDOR)  
During the security assessment, an Insecure Direct Object Reference (IDOR) vulnerability w as 
identified. It was observed that by modifying the username parameter in the request, the 
application returned data without performing proper authorization checks. For example, 
when the value of the userid parameter was changed from:  
userid: “ 2e23ed22 -c3d3-457f -8362 -d7263c9fa06d”  
to userid : “2e23ed22 -c3d3 -457f -8362 -d7263c9fa08d”  
the application returned the same data, indicating that access control checks were not 
enforced on the server side. This behavior demonstrates a Broken  Access Control 
vulnerability, as unauthorized users may be able to access or manipulate data belonging to 
other users by simply altering request parameters. An attacker could exploit this issue to 
access sensitive information of other users, leading to da ta exposure, privacy violations, and 
potential regulatory non -compliance. To address this issue, it is strongly recommended to 
enforce proper server -side authorization checks for all user -controlled parameters; ensure 
that access to resources is validated against the authenticated user’s permissions; avoid 
relying on client -supplied identifiers for access control decisions; and implement indirect 
object references or secure access tokens where applicable.
